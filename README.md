# Simple MCP

Приватний MCP-сервер для WordPress. Дає AI-асистенту (Claude Code) працювати з сайтом
«наче він локальний»: доступ до **WP-CLI** (для адмінів) + безпечні інструменти для **медіа**,
**Gutenberg-блоків** та **ACF** — через власний ендпоінт **поза** WP REST API.

Доступ — **персональними ключами**: кожен ключ належить конкретному WordPress-користувачу
й дзеркалить його роль. Що може ключ, вирішують (1) матриця «Права ролей» у налаштуваннях
плагіна і (2) нативні capabilities WordPress для typed-операцій над об'єктами.

> Не для публікації. Для власних проєктів.

Автор: [Vitalii Kaplia](https://kaplia.pro/) · Поточна версія: **2.5.3**.

## Чому не готовий плагін

Проаналізовано `ai-engine`, `easy-mcp-ai`, `royal-mcp`. Усі:
- сидять на **WP REST API** (а якщо REST вимкнено для анонімів — їхній ендпоінт не працює);
- **не мають** WP-CLI passthrough;
- несуть баласт (OAuth-сервери, 5–7 таблиць, SEO/GA4/WooCommerce, телеметрію, upsell).

Simple MCP бере з них найкраще (`media_handle_sideload`, `wp_slash`+round-trip verify,
ACF через `update_field`, hashed-токен, rate-limit, audit-log) і викидає решту.

## Встановлення

1. Плагін лежить у `wp-content/plugins/simple-mcp`. Активуй у **Плагіни**.
2. **Налаштування → Simple MCP** → перевір шлях ендпоінта (типово `simple-mcp`), матрицю
   **«Права ролей»**, rate-limit, IP-allowlist і шляхи до `wp`/CLI-`php`.
3. **Профіль користувача → Simple MCP — ключ доступу** → «Згенерувати ключ». Скопіюй
   (показується раз, разом із готовою командою підключення).
4. Якщо ролі потрібен `wp_cli`, перевір, що `wp` доступний веб-серверу і `proc_open` не вимкнено.

## Модель доступу: користувач → роль → ключ

- **Ключ персональний** (`smcp-{user_id}-…`), генерується на сторінці профілю користувача
  (свого — кожен сам; будь-чийого — адмін на екрані редагування користувача). У БД лише SHA-256.
- Автентифікований HTTP-запит виконується **від імені власника ключа**
  (`wp_set_current_user`). Типізовані операції над WordPress-об'єктами додатково перевіряють
  його нативні права:
  автор не відредагує чужий пост, редактор не запише опції (`manage_options`), публікація
  вимагає `publish_posts` і т.д.
- **Матриця «Права ролей»** в налаштуваннях вмикає групи інструментів per-role (включно з
  кастомними ролями): ядро контенту, блоки, мультимовність, контент і дискавері, `wp_cli`,
  серверні операції. Вимкнена група повністю прихована від агента (`tools/list` і виклики).
- `wp_cli` запускається окремим привілейованим процесом і **не успадковує** object-level права
  користувача з HTTP-запиту. Тому `wp_cli` і серверні операції мають **хард-лімит**: лише ролі
  з `manage_options` (на multisite — лише супер-адміни); для інших це була б ескалація привілеїв.
- Кілька ролей у користувача = об'єднання їх дозволів. Зміна ролі міняє права ключа миттєво
  (права резолвляться на кожен запит, не «запікаються» в ключ).
- **Сторінка налаштувань і матриця — лише для адмінів** (`manage_options`); посилання
  «Налаштування» на екрані Плагіни теж бачать тільки адміни. Звичайні користувачі бачать
  на сайті лише секцію власного ключа у своєму профілі.

### Ключі в профілі користувача

**Профіль (`profile.php`) → «Simple MCP — ключі доступу».** Тут кожен користувач із MCP-доступом
керує **своїми** ключами; адмін відкриває цю ж секцію на екрані редагування будь-кого
(`user-edit.php`).

- Показано, які групи інструментів дає роль користувача, і чи має роль MCP-доступ узагалі.
- **До 10 іменованих ключів** на користувача (наприклад, окремо для ноутбука й робочого ПК).
  Для кожного видно назву, коли й ким створено, коли й з якого IP востаннє використано
  (оновлюється не частіше ніж раз на 5 хвилин).
- **Згенерувати ключ** (з назвою) — plaintext та готова команда `claude mcp add …` показуються
  **один раз** (транзієнт до 5 хвилин, прив'язаний і до того, хто генерує, і до власника ключа);
  у БД лягає лише SHA-256. Новий ключ **не** інвалідовує наявні.
- **Відкликати** — один конкретний ключ або всі одразу; підключення з цим ключем зупиняється миттєво.
- Ключ, створений до 2.5.0, працює далі й показується окремим рядком «legacy» (його можна відкликати).
- Генерація й відкликання ключів пишуться в журнал викликів (хто, кому, який ключ).
- Видалення користувача автоматично прибирає його ключі (`uninstall`/`wp_delete_user`).

## Підключення в Claude Code

```bash
claude mcp add --transport http simple-mcp https://САЙТ/simple-mcp \
  --header "Authorization: Bearer ВАШ_ПЕРСОНАЛЬНИЙ_КЛЮЧ"
```

Готова команда з реальним ключем показується при генерації в профілі.
Для локалки без HTTPS додай у `wp-config.php`: `define('SIMPLE_MCP_ALLOW_INSECURE', true);`
За TLS-проксі (Cloudflare, балансувальник) замість цього вкажи адреси проксі в
`SIMPLE_MCP_TRUSTED_PROXIES` — тоді HTTPS і IP клієнта беруться з `X-Forwarded-Proto` /
`X-Forwarded-For`, але лише від цих адрес.

> **Тільки локальний клієнт (Claude Code CLI).** Плагін автентифікується статичним
> Bearer-ключем і **не** реалізує OAuth-сервер, тож хмарний веб-інтерфейс claude.ai
> (**Settings → Connectors → Add custom connector**) підключити його **не може** — той
> потік очікує OAuth. Локальний сайт (`*.test`/`localhost`) з хмари теж недоступний.
> Використовуй **Claude Code** на машині, що бачить сайт; для віддалених інсталяцій —
> публічний HTTPS-домен. Перевірка: `claude mcp list` → `simple-mcp: ✓ Connected`.

Основний спосіб автентифікації — `Authorization: Bearer …`. Якщо проксі/FPM зрізає
`Authorization`, підтримується запасний заголовок `X-Simple-MCP-Key: ВАШ_КЛЮЧ`.

## Транспорт

- MCP **Streamable HTTP** + **JSON-RPC 2.0**. Підтримувані версії протоколу: `2025-11-25`,
  `2025-06-18`, `2025-03-26`. `initialize` повертає версію клієнта, якщо вона підтримується,
  інакше — `2025-11-25`. Заголовок `MCP-Protocol-Version` перевіряється (непідтримувана версія → 400).
- Шлях ендпоінта налаштовується в адмінці (типово `/simple-mcp`) і ловиться на
  `do_parse_request` — **не** через `register_rest_route`,
  тому вимкнений REST API на анонімів на нього не впливає.
- Методи: `initialize`, `tools/list`, `tools/call`, `ping` (health-check — це `ping`).
- Сервер не відкриває SSE-потік: автентифікований `GET`/інші методи → `405` з `Allow: POST`;
  без валідного ключа такі запити повертаються у звичайний WordPress routing (типово 404).
- Батчі JSON-RPC приймаються лише для `2025-03-26` (до 10 повідомлень, кожен `tools/call`
  рахується в rate-limit); для `2025-06-18`+ батч → 400, як вимагає специфікація.
- Нотифікації й відповіді клієнта → `202` без тіла. Якщо заголовок `Origin` присутній і не
  збігається з сайтом → 403 (додаткові origin-и — фільтр `simple_mcp_allowed_origins`).
- HTTP-статуси для `POST`: без ключа або з невалідним/відкликаним ключем → `401` (`WWW-Authenticate: Bearer`,
  для невалідного — `error="invalid_token"`); роль без MCP, IP поза allowlist, не HTTPS → 403;
  rate-limit і блокування IP → 429 з `Retry-After`; kill-switch → 503.
- Фатальна PHP-помилка всередині інструмента повертається як JSON-RPC `-32603` із `id` запиту
  й пишеться в журнал.
- Результати інструментів: компактний JSON у `content` + `structuredContent` (MCP 2025-06-18).
  Кожен інструмент має `title` і `annotations` (`readOnlyHint`/`destructiveHint`/…), тож клієнт
  може автоматично дозволяти read-only виклики. Аргументи перевіряються за `inputSchema`
  (невідомі ключі, типи, обов'язкові поля) — помилка повертається звичайним `isError`-результатом.

## Інструменти

> 📖 **Повний гайд для агентів:** [docs/MCP-GUIDE.md](docs/MCP-GUIDE.md) — модель контенту,
> рецепти й пастки (як не зламати блоки, мультимовність, опції). Ключові правила також
> прокидуються агенту через MCP `instructions` при підключенні.

**Ядро** (група «MCP-доступ» — доступна кожній ролі з MCP; нативні права перевіряються на кожен об'єкт)

| Інструмент | Призначення |
|---|---|
| `wp_cli` | Привілейований WP-CLI (без «wp»), лише для ролей з `manage_options`. Deny-list, блок метасимволів, `@alias`, `cli`/`package`; без «Серверних операцій» сімейства plugin/theme/core/language/config/… дозволяють лише читання. |
| `get_post` / `update_post` | Читання (з `etag`) / block-safe запис тіла й полів поста: title, slug, excerpt, date, parent, menu_order, thumbnail, meta, status (кошик/відновлення через нативні `wp_trash_post`/`wp_untrash_post`); одне збереження під lock, `if_match`, ревізія або бекап. |
| `find_posts` | Пошук постів (тип, статус, текст, мова, parent, автор, ids) — лише ті, які користувач може читати. |
| `set_post_terms` | Призначити терми посту (id або slug/назва; `append`, `create_missing`). |
| `revision_list` / `revision_restore` | Список ревізій і meta-бекапів поста / відкат до них (під lock, `if_match`). |
| `cache_flush` | Скинути кеш поста (W3TC, WP Super Cache, LiteSpeed, WP Rocket, …) або всього сайту (`manage_options`). |
| `acf_get` / `acf_update` | ACF на **пості/user/term/comment/опціях** (не блокові поля). Поле резолвиться лише серед груп, що прив'язані до цілі; per-language опції через `lang`. |
| `upload_media` · `upload_begin` · `upload_chunk` · `upload_finish` | Медіа через `media_handle_sideload` → **ресайз + webp**. Chunked для великих (до 1 GB): сесія прив'язана до користувача, `index` для ідемпотентних повторів, base64 можна різати будь-де, перевірка `size`/`sha256`. |

**Блоки** (ACF-поля всередині Гутенберг-блоків — inline в `post_content`)

| Інструмент | Призначення |
|---|---|
| `block_get` / `list_block_fields` | Дерево блоків сторінки з `path` (включно з вкладеними в core/group/columns), `content_etag`, опційно `nested:true` у формі для запису / схема полів блоку (з ACF-реєстру, з дефолтами). |
| `block_update` | Правка ACF-полів блоку: **злиття** за замовчуванням (`replace:true` — повна заміна), пласкі шляхи (`tiles_0_title`), повна валідація за типами полів, `dry_run`, `if_match`. |
| `block_insert` / `block_move` / `block_remove` / `block_replace` | Структура сторінки з JSON-специфікацій: дефолти полів і блоку підставляються, вкладені блоки через `parent_path`, `dry_run`, `if_match`. |
| `block_batch` | Кілька операцій над блоками одного поста — одним збереженням, усе-або-нічого. |

**Мультимовність** (детект wp-loc/WPML)

| Інструмент | Призначення |
|---|---|
| `wploc_get_translations` / `wploc_link_translation` / `wploc_create_translation` | Резолв/лінк/створення перекладів постів і термів: строгі коди мов, перевірки слотів перед лінком, переклад зберігає статус/автора/пароль джерела й мапить parent, терми, мініатюру та ACF-зв'язки. |

**Контент і дискавері**

| Інструмент | Призначення |
|---|---|
| `create_post` | Створити пост/сторінку/CPT з block-safe тілом (валідація статусу/типу/parent/thumbnail, meta з нативними meta-caps, мова на мультимовних сайтах). |
| `render_post` | Рендер HTML для верифікації: як на фронті (`the_content`) або лише `do_blocks`. |
| `safe_delete` | Translation-aware видалення: справжній кошик для будь-якого типу, переклади не каскадяться (пост від'єднується від групи). |
| `term_list` / `term_create` / `term_update` | Терми таксономій (права як у REST-контролері термів WordPress). |
| `describe_site` | Схема форку: блоки+поля, ACF-опції з post_id для кожної мови, CPT/таксономії, мовна мапа; кеш 1 год, `refresh:true` перебудовує. |

Видалення термів і plain Settings-API options виконуються через `wp_cli`, якщо ця група
доступна ролі. Типізовані `acf_*` працюють зі значеннями ACF термів/опцій, а `wploc_*` — зі
зв'язками перекладів.

### Права ролей (матриця в адмінці)
**Налаштування → Simple MCP → Права ролей.** Одна таблиця: рядки — групи інструментів,
колонки — всі ролі (включно з кастомними). Вимкнена для ролі група повністю прихована від
агента (не в `tools/list`, не викликається), а `instructions` при конекті підлаштовуються
під конкретного користувача:
- **MCP-доступ (ядро контенту)** — головний тумблер ролі; off = роль без MCP взагалі.
- **`wp_cli`**, **Серверні операції** — лише для ролей з `manage_options` (хард-лімит).
- **Блоки**, **Контент і дискавері** — за потреби.
- Ядро (`find_posts`, `set_post_terms`, `revision_*`, `cache_flush`, `get/update_post`, `acf_*`,
  `upload_*`) доступне кожній ролі з MCP-доступом: нативні права обмежують його об'єктами, які
  користувач і так може змінювати в адмінці.
- **Мультимовність** — з **авто-детектом**: якщо WP-LOC/WPML нема — група прихована для всіх.

Дефолти дзеркальні: administrator — усе (server ops off); editor — ядро контенту + блоки +
мультимовність + контент і дискавері (усе, крім `wp_cli` і серверних операцій); author —
лише ядро (нативні caps обмежують його своїми постами); решта (включно з кастомними) — off.

## Безпека

- **HTTPS-only** (крім `SIMPLE_MCP_ALLOW_INSECURE` для локалки; за проксі — `SIMPLE_MCP_TRUSTED_PROXIES`).
- **Персональні ключі**: `smcp-{user_id}-{64 симв.}`, у БД лише **SHA-256** (user meta),
  звірка `hash_equals`. Основний транспорт секрету — `Authorization: Bearer`; запасний, якщо
  цей заголовок зрізає проксі, — `X-Simple-MCP-Key`. Ключ ніколи не передаємо в URL, щоб він
  не тікав у логи/проксі. Відкликання — кнопкою в профілі; видалення користувача теж
  інвалідовує ключі.
- **Два шари авторизації typed tools**: матриця ролей (які групи інструментів видно) + нативні
  WordPress-capabilities на кожну операцію над WP-об'єктом (`edit_post` на конкретний пост,
  `publish_posts`, `upload_files`, `manage_options`, `delete_post`, meta-caps для post meta, …).
  Читання без прав редагування — лише опубліковане, без пароля і лише публічних типів записів
  (приватні CPT на кшталт журналів пошти чи бронювань потребують `edit_post`). `wp_cli` —
  навмисний привілейований виняток, тому окремо обмежений `manage_options`-ролями
  (на multisite — супер-адмінами).
- **Deny-list** для руйнівних команд (`db drop`, `db reset`, `site empty`, `eval`, …) —
  спільний для всіх ключів. Синоніми WP-CLI нормалізуються перед перевіркою (`plugin upgrade` =
  `update`, `theme uninstall` = `delete`, `sql` = `db`, `db dump` = `export`, …).
- **Серверні операції** за замовчуванням **вимкнені**, і тоді сімейства `plugin`, `theme`, `core`,
  `language`, `config`, `maintenance-mode`, `scaffold`, `i18n`, `server` дозволяють **лише читання**
  (`list`/`get`/`status`/`is-installed`/`path`/`search`/`version`/`verify-checksums`/…). Вмикаються
  в матриці per-role (конфіг і набір плагінів законно різняться між середовищами; тема сайту й
  Simple MCP мають окремі versioned sources). `DISALLOW_FILE_MODS` вимикає їх для всіх. Руйнівне
  агент має **перепитувати**.
- **Завжди заблоковано** в `wp_cli`: `@alias` на місці команди, сімейства `cli` (крім
  `cli version|info`) і `package`, глобальні прапорці `--path`, `--exec`, `--require`, `--ssh`,
  `--http`, `--prompt`. WP-CLI працює з окремим HOME на кожен сайт (порожній конфіг, без
  пакетів; у системному temp, а якщо він недоступний — у temp WordPress або
  `uploads/simple-mcp-tmp`; каталог, доступний іншим користувачам, відкидається), stdin =
  `/dev/null`, вивід обмежено 1 MB на потік; ненульовий код виходу чи таймаут → `isError`.
- **Rate-limit** по користувачу (типово 120/хв; `0` вимикає; атомарні лічильники), блокування IP
  (IPv6 — цілої мережі /64) після 10 невдалих автентифікацій за 5 хвилин: невалідний токен з такої
  адреси отримує 429, а валідний ключ проходить. Опційний **IP-allowlist**: IPv4/IPv6 у будь-якому
  записі та IPv4/IPv6 CIDR. Джерело IP — `REMOTE_ADDR` (або `X-Forwarded-For` лише від
  `SIMPLE_MCP_TRUSTED_PROXIES`): за проксі/CDN без цієї константи всі клієнти мають адресу проксі й
  ділять один лічильник невдач.
- **Audit-log** кожного `tools/call` з прив'язкою до користувача й ключа, тривалістю і деталями
  (таблиця `{prefix}simple_mcp_log`). Секрети в аргументах редагуються (паролі, токени, значення
  `config`/`option`/`site option`/`… meta` і `… patch` для секретних імен — і всередині JSON-значень,
  `--user_pass V`, логін:пароль і query-рядок у URL, base64 → `<base64 N chars>`), довгі аргументи
  безпечно обрізаються до 2000 байтів. Також пишуться невдалі автентифікації (не більше 60 рядків за
  5 хвилин на весь сайт), виклики невідомих інструментів, фатальні помилки та генерація/відкликання
  ключів.
  Перегляд у **Налаштування → Simple MCP → Останні виклики**: фільтр за діапазоном дат
  (від/до), пагінація (10 записів на сторінку) і кнопка «Очистити лог». Ретенція налаштовується
  (типово 30 днів, `0` — зберігати завжди) і рахується за часом сайту; чистить щоденний WP-Cron
  (з `DISABLE_WP_CRON` потрібен системний cron).
- **Kill-switch**: `define('SIMPLE_MCP_DISABLE', true);` у `wp-config.php`.
- SSRF-захист на завантаження з URL (блок приватних діапазонів), ліміт 1 GB / 60 с.

> `wp_cli` — це керований **RCE за задумом**, тому він структурно недоступний ролям без
> `manage_options`. Адмінський ключ = адмін-пароль. Рекомендація: обкатати на
> **локалці → staging**, на проді — IP-allowlist/VPN і ключі з мінімально потрібними ролями.

**Про deny-list.** Команди виконуються токенізовано, **без шелла** (`proc_open` argv),
тож чейнінг (`;`, `&&`, `` ` ``, `$()`), лапкові трюки (`db "drop"`), провідні глобальні
прапорці (`--quiet db drop`), синоніми команд і `@alias` не обходять фільтр. Але з увімкненим
`wp_cli` deny-list — це **запобіжник від випадковостей, а не пісочниця**:
адмін із ключем все одно може досягти руйнівного ефекту іншою командою (напр. `db query`).
Це прийнята модель (адмінський ключ = повний доступ). Так само й вимкнені «Серверні операції»
блокують **команди**, а не **ефекти**: `db export <шлях>`, `export --dir`, `search-replace --export`
пишуть файли, `option update active_plugins` чи `db query` змінюють стан плагінів через БД.
`wp_cli` — лише для повністю довірених адмінів. Хочеш жорсткого обмеження — видай ключ
користувачу з вужчою роллю (editor/author): він працюватиме лише типізованими інструментами
в межах своїх нативних прав.

**Про `upload_media` з `url`.** Є SSRF-гейт (схема http/https + перевірка A/AAAA на приватні
діапазони) плюс core `wp_safe_remote_get`. Залишковий ризик — DNS-rebinding, тому для
**недовірених** джерел завантажуй через `base64`, а не `url`.

## Авто-оновлення через GitHub

Плагін оновлюється стандартним механізмом WordPress із **GitHub Releases** публічного
репозиторію [`vitaliikaplia/simple-mcp`](https://github.com/vitaliikaplia/simple-mcp):

- Останній реліз читається з GitHub API (`releases/latest`), версія — тег без `v` (`v2.5.0` → `2.5.0`).
  Перевірка — коли WordPress оновлює свій список оновлень, кеш 12 год (невдала — 1 год; ручна
  **Оновлення → Перевірити знову** передає `?force-check=1`). Звичайні сторінки мережу не чіпають.
- Пакет — asset `simple-mcp.zip` релізу; перед встановленням його **SHA-256 звіряється** з
  asset-ом `simple-mcp.zip.sha256`. Розбіжність або відсутня контрольна сума скасовують оновлення
  (fail closed); реліз без обох assets не пропонується.
- Вікно «Подробиці» показує changelog **нового** релізу (з release notes).
- Заголовок `Update URI` гарантує, що wordpress.org ніколи не запропонує «оновлення» з тим самим slug.
- SHA-256 захищає завантаження і прив'язує його до незмінного asset-а тегу, але не від
  скомпрометованого GitHub-акаунта (обидва assets вантажить той самий акаунт). Рекомендовано
  увімкнути в репозиторії «immutable releases»; підпис релізів — можливий наступний крок.

**Як випустити реліз:**
1. Підняти `Version:` і `SIMPLE_MCP_VERSION` у `simple-mcp.php`, «Current release» в `AGENTS.md`,
   «Поточна версія» вгорі README і додати новий верхній запис `### X.Y.Z — <назва>` у «Зміни».
2. `php bin/check-version.php vX.Y.Z`, `php tests/run.php`, `php bin/lint.php`.
3. Закомітити (з новими файлами), запушити гілку й дочекатися зеленого CI (тести на PHP 8.1–8.5,
   живий WordPress на 8.1 і 8.5, захист на 7.4/8.0), потім `master`, потім
   `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. GitHub Actions (`release.yml`) лінтить і тестує на PHP 8.1 і 8.5, звіряє версію з тегом, збирає
   `simple-mcp.zip` (`git archive` без сторонніх actions, dev-файли виключені через `.gitattributes`),
   розпаковує його й перевіряє (`bin/check-package.php`: усі файли, які підключає `simple-mcp.php`, на
   місці, кожен PHP-файл проходить `php -l`), рахує SHA-256 і публікує реліз із нотатками з README
   (право на запис має лише крок публікації). Сайти на 2.5.0+ бачать оновлення лише після появи
   цього релізу (про 2.4.0 і старіші — див. вище).

Dev-канал: `define('SIMPLE_MCP_UPDATE_CHANNEL', 'branch');` — старий режим (версія з `Version:`
гілки `SIMPLE_MCP_GITHUB_BRANCH`, типово `master`, zip гілки, **без** контрольної суми).

**Перехід з 2.4.0 і старіших.** Встановлені 2.4.0 і старіші ще мають старий оновлювач: він читає
`Version:` з `master` і ставить zip гілки `master` без жодної перевірки, щойно там версія вища. Тож
для них **пуш у `master` і є релізом** — незалежно від CI, тегу й релізу. Для 2.5.0: закомітити всі
потрібні файли (`git add -A`; `git status --porcelain` не має показувати `??` для `includes/`),
спершу запушити коміт в окрему гілку й дочекатися зеленого CI (PHP 8.1–8.5), потім fast-forward
`master` і одразу запушити тег `v2.5.0`. Сайти на 2.5.0+ оновлюються вже лише з релізів (SHA-256).

## Константи (`wp-config.php`)

| Константа | Дія |
|---|---|
| `SIMPLE_MCP_DISABLE` | `true` — миттєво вимкнути сервер. |
| `SIMPLE_MCP_ALLOW_INSECURE` | `true` — дозволити HTTP (лише для локалки). |
| `SIMPLE_MCP_TRUSTED_PROXIES` | IP/CIDR довірених проксі (рядок через кому/пробіл або масив): лише від них беруться `X-Forwarded-For` і `X-Forwarded-Proto`. |
| `SIMPLE_MCP_WP_BIN` | Шлях до бінарника `wp`. Має пріоритет над полем у налаштуваннях і вимикає його. |
| `SIMPLE_MCP_PHP_BIN` | Шлях до CLI-`php` для wp-cli. Має пріоритет над полем у налаштуваннях і вимикає його. |
| `SIMPLE_MCP_UPDATE_CHANNEL` | `'branch'` — dev-канал оновлень із гілки без контрольної суми (типово — GitHub Releases). |
| `SIMPLE_MCP_GITHUB_BRANCH` | Гілка для dev-каналу (типово `master`). |

Шлях у полі налаштувань приймається, лише якщо він абсолютний, файл існує і називається
`php`/`php8.x`/`php8x` або `wp`/`wp-cli`/`wp-cli.phar`; інакше ігнорується й діє автовизначення.
Під `open_basedir` (типово на хостингу) PHP сайту не бачить `/usr/local/...`, тому такий шлях
перевіряється пробним запуском (`php` має відповісти як CLI, `wp` — як WP-CLI); результат кешується.
Автовизначення шукає CLI-`php` тієї ж версії major.minor, що обслуговує сайт (Herd: `php85-fpm` →
`php85`; Debian: `php-fpm8.3` → `php8.3`; далі `PHP_BINDIR`, Homebrew, системні та панельні шляхи),
перевіряє запуском і кешує на добу (з оновленням плагіна — шукає заново).

## Вимоги

PHP **8.1+**, WordPress 6.0+, WP-CLI на сервері (для `wp_cli`) і доступний `proc_open`.
ACF-інструменти — за наявності ACF. Перевірено з WordPress 7.0.

PHP 8.1 перевіряється в CI на кожен коміт: тести й лінт на 8.1–8.5 і живий WordPress на 8.1 і 8.5
(`tests/e2e/`). На PHP, старішому за 8.1, WordPress сам не активує й не оновлює плагін. Якщо ж PHP
понизили вже після активації або WP-CLI запущено старішим CLI-php, плагін нічого не завантажує й
показує адмінам повідомлення замість фатальної помилки.

## Зміни

### 2.5.3 — підтримку PHP 8.1 перевірено на живому WordPress

- Мінімальна версія PHP — **8.1**, як і раніше в заголовку `Requires PHP`. Тепер це перевірено
  на ділі. Код не використовує нічого з PHP 8.2+: ні функцій, класів і констант, ні синтаксису, ні
  поведінки, що змінилась після 8.1. Лінт проходить навіть на PHP 8.0.
- Новий CI-джоб «WordPress smoke» на PHP 8.1 і 8.5: справжній WordPress із MySQL і запити до
  ендпоінта по HTTP, як від MCP-клієнта, — понад 130 перевірок. Покриває автентифікацію, версії протоколу
  й батчі, `tools/list`, типізовані інструменти на тестовому пості (блоки, рубрики, ревізії, медіа,
  видалення) і `wp_cli`. Будь-яке попередження, нотис чи deprecation PHP з файлів плагіна валить збірку.
- Якщо PHP сервера старіший за 8.1 (понизили після активації або WP-CLI запущено старішим CLI-php),
  плагін більше не валить сайт фатальною помилкою: нічого не завантажує й показує адмінам
  повідомлення. Перевіряється в CI на PHP 7.4 і 8.0.
- **Виправлено (на PHP 8.1–8.2):** SSRF-фільтр `upload_media` з `source: "url"` пропускав хост, чий
  AAAA-запис — IPv4-mapped IPv6 (`::ffff:127.0.0.1`, `::ffff:169.254.169.254`): до PHP 8.3 `filter_var`
  не вважав такі адреси зарезервованими. Тепер перевірка однакова на всіх версіях. Заодно
  відкидаються IPv4, загорнуті в NAT64 і 6to4, і CGNAT `100.64.0.0/10` (тест `tests/test-ssrf.php`).

### 2.5.2 — вирівняна таблиця ключів у профілі

- **Виправлено:** у таблиці ключів у профілі користувача заголовки були зсунуті відносно рядків
  (вкладена таблиця успадковувала стилі `.form-table th/td` сторінки профілю: ширину 200px і
  асиметричні відступи). Тепер у таблиці власні рівні відступи й вирівнювання.
- На мобільному кожен ключ показується карткою з підписами полів («Створено», «Ким», «Останнє
  використання») замість таблиці, що розпирала сторінку ширше за екран.

### 2.5.1 — виправлено wp_cli на хостингу з open_basedir

- **Виправлено (регресія 2.5.0):** на хостингу з `open_basedir` не працював `wp_cli` і пошук CLI-php.
  У 2.5.0 stdin дочірнього процесу відкривався як файл `/dev/null`, а `proc_open` відкриває його в
  процесі PHP — поза `open_basedir`, тож запуск падав. Тепер stdin — одразу закритий pipe (той
  самий EOF для команд).
- **Виправлено:** робочі шляхи до `php` / `wp` (наприклад `/usr/local/php85/bin/php`,
  `/usr/local/bin/wp`) відхилялись у налаштуваннях як «невалідні», бо під `open_basedir`
  `is_file()` їх не бачить. Тепер такий шлях перевіряється пробним запуском (ім'я файлу все одно
  має бути `php*` / `wp*`); так само автовизначення `wp`.
- Невидимий через `open_basedir` WP-CLI запускається через обраний php з прихованими PHP-нотисами,
  тож у stdout команд не потрапляють `Deprecated: …` (важливо для `--format=json`).
- Кеш автовизначення php скидається з оновленням плагіна — хибне «не знайдено» з 2.5.0 не лишається.
- Регресійний тест запускає дочірній PHP з `open_basedir` (`tests/test-shell.php`).

### 2.5.0 — повне рев'ю: безпечні видалення й переклади, злиття блоків, релізи з контрольною сумою

Результат повного рев'ю коду (109 підтверджених знахідок, звіт —
[docs/REVIEW-2026-10-01.md](https://github.com/vitaliikaplia/simple-mcp/blob/master/docs/REVIEW-2026-10-01.md)).
Усі виправлено.

**Втрата даних (критичне)**
- `safe_delete` більше не стирає переклади: wp-loc на будь-якому остаточному видаленні (і при
  очищенні кошика через 30 днів) видаляв усю групу перекладів. Тепер пост спершу від'єднується від
  групи. Без `force` пост справді йде в кошик для **будь-якого** типу (раніше CPT і медіа
  видалялись назавжди з відповіддю `trashed: true`); результат звіряється з фактичним станом.
- `wploc_create_translation` більше не знімає з публікації оригінал: переклад створюється зі
  статусом, автором, паролем і датами джерела (синхронізація атрибутів wp-loc інакше штовхала
  `draft` і порожній пароль на живу сторінку). Терми, parent, мініатюра й ACF-зв'язки мапляться на
  мову перекладу; meta копіюється побайтово.
- `block_update` **зливає** значення: частковий `set` групи чи рядка репітера більше не стирає
  інші підполя (`replace:true` — стара повна заміна). Пласкі шляхи (`tiles_0_title`), `dry_run`.
- `block_insert`/`block_replace` підставляють дефолти полів і блоку — нові блоки більше не
  ховаються темою (раніше бракувало `responsive_options`).
- Паралельні записи: lock на пост + `if_match`/`content_etag` в усіх записах блоків, `update_post`,
  `revision_restore`.
- Редагування перекладу не в мові за замовчуванням (будь-який запис блоків, `update_post`,
  `revision_restore`, `set_post_terms`, кошик у `safe_delete`) більше не підміняє й не додає йому
  категорії мови за замовчуванням: поза адмінкою wp-loc підміняв ID термів, а синхронізація
  термів розносила це на всю групу (вада була і в 2.4.0).
- `update_post` зі `status:"trash"` для поста з перекладами відмовляє (синхронізація wp-loc
  відправила б у кошик усю групу) — для цього є `safe_delete {allow_cascade:true}`. Пости в кошику
  не редагуються жодним записом, доки їх не відновлено.
- Аудит-лог більше не губить рядки з кирилицею (обрізання розрізало символ, і `wpdb` мовчки
  відкидав INSERT).
- Резервна копія тіла (`_simple_mcp_backup`) більше не псує `\uXXXX` (була без `wp_slash`);
  тепер це кільце з 5 копій. `acf_update` зберігає бекслеші.
- `block_update` з кількома шляхами рядків в одному `set` (`{tiles_2:null, tiles_3:null}`)
  видаляв/правив не ті рядки: індекси рахувались після попереднього ключа. Тепер індекси завжди
  відносяться до блоку до виклику, видалення рядків застосовуються наприкінці, а ключ усередині
  видаленого рядка чи списку, який замінює інший ключ, відхиляється як конфлікт.
- `acf_update` для repeater/flexible/group/clone звіряє значення зі схемою до запису: невідоме
  під-поле, рядок-не-об'єкт чи невідомий `acf_fc_layout` — помилка зі шляхом (ACF мовчки відкидав
  такі дані й обрізав репітер, а виклик повертав успіх). Якщо ACF зберіг не стільки рядків, скільки
  надіслано, попереднє значення відновлюється й виклик падає.

**Безпека**
- `can_read_post`: опубліковане читається без прав редагування лише для публічних типів записів і
  без пароля (раніше автор міг читати журнали пошти, бронювання та запаролені сторінки).
- Гейт `wp_cli`: синоніми команд нормалізуються, `@alias`, `cli`, `package`, `--path`, `--prompt`
  заблоковані; без «Серверних операцій» сімейства plugin/theme/core/… — лише читання (раніше
  проходили `plugin uninstall`, `plugin upgrade`, `core update <zip>`, `package install`).
  Окремий HOME для WP-CLI на сайт, stdin `/dev/null`, ліміт виводу, `isError` при помилці.
- Multisite: `wp_cli` і серверні операції — лише супер-адмінам. `DISALLOW_FILE_MODS` вимикає
  серверні операції.
- Шляхи `wp`/`php` з налаштувань перевіряються; константи мають пріоритет.
- JSON-RPC батчі обмежені й рахуються в rate-limit; блокування IP після невдалих спроб замість
  `usleep`; IP-allowlist перевіряється першим; IPv6 і IPv6 CIDR; довірені проксі.
- `create_post`/`update_post` пишуть meta лише з нативними meta-caps; `upload_chunk` перевіряє
  `upload_files` і власника сесії; `acf_get` не віддає секрети з об'єктів і перевіряє права
  сторінки опцій.
- Блокування IP після невдалих спроб не зачіпає валідні ключі (за NAT/проксі сміттєві запити не
  блокують справжніх клієнтів); IPv6 рахується мережами /64; рядків аудиту про відмови — не більше
  60 за 5 хвилин на сайт. Аудит редагує секрети в `site option`, `… meta`, `… patch`, JSON-значеннях,
  `--user_pass V` і URL.
- `find_posts` показує адміністраторам і редакторам і чужі приватні записи (без `perm=readable`, який
  для кількох типів записів ховав їх) і не рахує вкладення, батьківський запис яких недоступний.
- `update_post {status:"trash"}` для вкладення відмовляє, коли `MEDIA_TRASH` вимкнено (як
  `safe_delete`): такий кошик не видно в медіатеці, а потім WordPress видаляє файли назавжди.
- HOME для WP-CLI перевіряється і без розширення posix: каталог чи `config.yml`, які може змінити
  інший користувач, відкидаються.

**Мультимовність**
- Строгий резолвер мов (slug, код, локаль, регістр); невідомі мови — помилка. Більше ніяких двох
  постів однієї мови в групі.
- `acf_update` спільних/copy-once контейнерів (repeater/group/flexible/clone) тепер доходить до
  перекладів, як у wp-admin (wp-loc синхронізує їх лише на `acf/save_post`), а результат перелічує
  переклади, куди мультимовний плагін записав значення (`translations_changed`).
- `wploc_get_translations`/`wploc_link_translation` без `kind`: ID, що є і постом, і `term_id`,
  означає пост, як у 2.4.0 (терм — `kind:"term"`); якщо такий терм є в перекладній таксономії,
  результат має `note`.
- `wploc_link_translation`: перевірки перед записом (зайнятий слот, інша група, оригінал),
  перечитування після запису. Терми — за `term_id`. `wploc_get_translations` повертає статуси й
  назви (**змінилась форма відповіді**).
- Per-language ACF-опції на wp-loc: `options` для мови за замовчуванням і `options_{slug}` для
  інших (селектор `options_uk` з гайду писав туди, звідки wp-loc не читає). Параметр `lang`.
- `create_post` одразу реєструє мову поста, тож wp-loc не створює автоматичні чернетки.

**Нові інструменти й можливості**
- `find_posts`, `set_post_terms`, `revision_list`, `revision_restore`, `cache_flush` (група ядра),
  `term_list`, `term_create`, `term_update` (контент), `block_batch` (блоки).
- `update_post`: slug, excerpt, date, parent, menu_order, thumbnail, meta; кошик і відновлення
  через нативні функції.
- Блоки: вкладені блоки (`path`, `parent_path`), `nested:true` у `block_get`, повна валідація за
  типами полів, seamless-клони й flexible layout meta — як зберігає ACF.
- Chunked upload: ідемпотентні повтори (`index`), base64 можна різати будь-де, перевірка
  `size`/`sha256`, ліміти на користувача, прибирання покинутих файлів.
- Кілька іменованих ключів на користувача з «останнім використанням».
- MCP: переговори версії протоколу (`2025-11-25`/`2025-06-18`/`2025-03-26`), `title` і
  `annotations` для всіх інструментів, `structuredContent`, перевірка аргументів за схемою,
  коректні HTTP-статуси.
- `render_post` за замовчуванням рендерить як фронт (`the_content`).

**Змінений формат результатів**
- `safe_delete`: `deleted` — тепер boolean (true лише для остаточного видалення; раніше — ID поста
  навіть для кошика), `outcome` — `trashed|deleted`; `siblings_left` — `{lang: {id, status}}` замість
  `{lang: id}`.
- `wploc_link_translation`: `linked` перейменовано на `target` (`{id, language, previous}`).
- `wploc_get_translations`: див. «Мультимовність».
- `render_post`: замість `length` — `bytes` (повний HTML) і `returned_bytes`; додано `mode`,
  `post_language`.
- `block_get`: `anchor` — `null`, коли якоря немає (раніше бувало `""`).
- Описи інструментів і MCP `instructions` не довші за 2048 символів (Claude Code обрізає довші), а
  застереження (JSON-кодування в `wp_cli`, sync wp-loc) стоять першими; перелік read-only підкоманд
  «Server ops» — у відмові гейта, формати значень `block_update` — в описі параметра `set`.

**Оновлення й реліз**
- Оновлення лише з GitHub Releases з перевіркою SHA-256 (`Update URI`, dev-канал через
  `SIMPLE_MCP_UPDATE_CHANNEL`). CI (lint на PHP 8.1–8.5, тести, звірка версій) і автоматичний
  реліз із тегу (перевірка на PHP 8.1 і 8.5, перевірка розпакованого zip). Сайти на 2.4.0 і
  старіших ще оновлюються старим способом — див. «Перехід з 2.4.0» в «Авто-оновлення».
- Міграція при першому завантаженні 2.5.0 не виконує ALTER аудит-таблиці у фронтенд-запитах: лише в
  адмінці, cron чи WP-CLI, одним запитом за раз (`GET_LOCK`) і одним `ALTER` на всі нові колонки.
- WP-CLI з `open_basedir` чи недоступним системним temp працює далі (HOME — у temp WordPress або
  `uploads/simple-mcp-tmp`; у крайньому разі без глобального конфігу, пакетів і кешу).
- Виправлено: cron ретенції журналу падав з `TypeError` на PHP 8 і ніколи не чистив лог;
  відновлюється, якщо зник.
- `uninstall` прибирає все: ключі, бекапи, тимчасові файли, HOME WP-CLI, усі сайти multisite.

### 2.4.0 — правильні ключі для полів із seamless-клонів

- **Виправлено:** `block_update`, `block_insert` і `block_replace` писали для полів, що потрапляють у
  блок через seamless-клон (спільна «шапка», група «Кнопки»), тимчасовий ключ ACF
  `<ключ клона>_<ключ поля>` замість власного ключа поля. ACF такий ключ не знаходить і мовчки
  відкидає значення на фронті — при цьому запис повертав `content_verified: true`. Тепер пишеться
  `__key` (як це робить сам ACF), і `list_block_fields` показує саме його.
- `block_update` лагодить такі зламані посилання в блоці, який редагує, і перелічує їх у
  `refs_repaired`.
- Запис, у якому нове посилання на поле не резолвиться в ACF, відхиляється з помилкою замість
  мовчазного збереження.
- **Виправлено (давня вада):** поле-група записувалось без порожнього батьківського значення, яке
  зберігає ACF (`"video_files":""` поруч із `"_video_files"`), тож `block_update` групи видаляв його,
  і `get_fields()` пропускав усю групу (наприклад, відео в медіа-блоці). Те саме — для клонів із
  режимом «group»: тепер вони пишуться так, як їх зберігає ACF.

### 2.0.0 — персональні ключі + дзеркалення ролей (breaking)

Повна переробка авторизації: замість одного глобального ключа — **персональні ключі, прив'язані
до WordPress-користувачів**, з дзеркаленням нативних ролей і прав.

- **Персональні ключі** (`smcp-{user_id}-…`) генеруються в профілі користувача; глобальний ключ
  прибрано. HTTP-запит виконується від імені власника ключа (`wp_set_current_user`).
- **Матриця «Права ролей»** в адмінці — вмикання груп інструментів per-role (включно з
  кастомними ролями). Дефолти дзеркальні (admin/editor/author). `wp_cli` і серверні операції —
  хард-лімит на ролі з `manage_options`.
- **Нативні capability-перевірки typed-операцій над WP-об'єктами**: `edit_post` на об'єкт,
  `publish_posts` (включно зі `status=future`), `delete_post` для кошика, `upload_files`,
  `manage_options` для опцій, cap таксономії для термів, `moderate_comments` для `comment_*`.
- **Журнал викликів**: колонка користувача, фільтр за датами, пагінація, кнопка очищення.
- **Сторінка налаштувань і посилання «Налаштування»** — лише для адмінів (`manage_options`).
- **Rate-limit** тепер рахується по користувачу (невалідні спроби — по IP).
- **Авто-міграція** зі старих глобальних тумблерів у матрицю ролей (працює і через reactivate,
  і через авто-оновлення); чистка старого ключа/транзієнтів у `uninstall`.
